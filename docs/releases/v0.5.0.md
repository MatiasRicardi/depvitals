# DepVitals v0.5.0 release notes

## Install and inspect scope

Requires Node.js **22.13.0 or newer**. Install the exact version and check it:

```sh
npm install --save-dev --save-exact depvitals@0.5.0
./node_modules/.bin/depvitals --version
```

The version command must print `0.5.0`. Keep the generated lockfile for CI. The simple `npx depvitals`
and global-install paths remain available; check which version they resolve before using new flags.

```sh
./node_modules/.bin/depvitals ./project --diagnostics
./node_modules/.bin/depvitals ./project --format json --diagnostics > depvitals-report.json
```

Run these commands from outside the selected project. The default terminal report and ordinary
JSON retain their existing contracts; JSON continues to identify its actual producer in
`tool.version`. `--diagnostics` appends scope facts from the existing scan, never evidence or
new findings. It is valueless, may appear once and cannot be combined with `--explain`.

- `sourceFilesScanned` counts successfully processed supported sources.
- `nestedPackageSourceFiles` counts those owned by a manifest below the selected root. Findings
  still use the selected root inventory. Select a child root to use its declarations, or make an
  intentional literal path exclusion and review the narrower result.
- Notice codes are ordered `no-supported-sources`, `nested-package-inputs`, `workspace-declared`.
  Workspace declarations are context; member patterns are not expanded or aggregated. A root with
  `workspaces` but no source/member directories can be clean and still report notices.

See the [reproduced examples and full grammar](../reference.md#scan-scope-diagnostics).
Diagnostic terminal and JSON scans bypass optional notifier cache/network access, including when
interactive. Core scanning remains static, offline and read-only.

## Editor feedback for project policy

The package includes [depvitals-config.schema.json](../../schemas/depvitals-config.schema.json),
a Draft 7 data asset for the two existing keys, `ignorePaths` and `ignoreDependencies`.
Use the [VS Code filename association](../reference.md#editor-validation) in workspace settings;
keep `$schema` out of the project instance. Use the installed local asset for offline editing
or the immutable v0.5.0 schema URL to pin validation to this release.

Editor validation checks structure and exact names; the CLI still enforces canonical config
selection, complete literal-path rules and normalization. Scoped roots such as `@scope/_demo`
and `@scope/-demo` are accepted under the existing 214-character grammar. Exclusions remain policy,
not proof of usage. A passing editor check does not certify that a path rule passes the CLI.

## JSON v1 and CI compatibility

Schema version stays **1**. Full diagnostic scans append one optional `diagnostics` object after
`query`; ordinary scans and explanations omit it. Counts, findings, package facts and evidence
retain their meanings. Consumers should tolerate unknown fields and check report/status and
semantic count/notice relationships in addition to the [schema](../../schemas/README.md).
The query pattern repair accepts scoped names already supported by the v0.4.1 CLI; it changes no
runtime query/exclusion grammar or dependency findings.

The [fixed-version CI recipe](../examples/ci/README.md) keeps ordinary capture by default and
provides an explicit diagnostic opt-in. Keep the minimal `npm run --silent check:dependencies`
command when consuming JSON. The exact, unchanged v0.4.1 verifier accepted unedited new diagnostic
artifacts in isolated installed-consumer tests. Reader compatibility does not make the old
published producer accept the new flag.

For diagnostic scans and the JSON CI capture:

| Outcome                                      | CLI exit | Artifact channels                                |                             CI verifier exit |
| -------------------------------------------- | -------: | ------------------------------------------------ | -------------------------------------------: |
| Clean, including scope notices               |        0 | Complete stdout report, empty stderr             |                                            0 |
| Dependency findings                          |        1 | Complete stdout report, empty stderr             |                                            1 |
| Argument/operational failure                 |        1 | Empty stdout, nonempty stderr, no partial counts | 1 for a valid operational-error artifact set |
| Missing, malformed or inconsistent artifacts |      n/a | Invalid captured set                             |                                            2 |

The verifier's exit 2 is an artifact-validation result, not a new CLI status. Upload available
artifacts before enforcement; capture-wrapper success alone does not mean a clean scan.

## Evidence and limits

The [six-root comparison](../compatibility/v0.5.0.md) binds four libraries and two application
exports to independently reviewed manifests, retained source and an
[expectation ledger](../../test/fixtures/external-corpus/v0.5.0/review.json). Findings,
ordinary terminal bytes, ordinary JSON values and ten explanation samples matched the installed
published v0.4.1 baseline. New scope facts agreed with the reviewed oracle. A deterministic
20,000-reference input also exercised full evidence serialization. Repeated fresh-process cost
observations apply only to the identified local host and inputs; they are not timing thresholds
or a general speed/memory claim. The comparison identifies an integration artifact before the
final version bump and release archive verification.

Remaining limits include one selected-root inventory, no workspace aggregation, alias/inherited
tsconfig resolution, blanket ambient-type inference, arbitrary executable tool configuration,
automatic fixes or CI baselines. Only supported source evidence creates missing findings;
script/config hints only suppress unused findings for eligible declarations. The reviewed ledger
keeps unsupported patterns and unresolved uses visible, including `xo`, `rollup`, and application
cases. A clean result is not proof of full coverage or safe dependency removal. Inspect evidence
and test project changes before editing the manifest.
